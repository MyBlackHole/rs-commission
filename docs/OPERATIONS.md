# 部署与资金操作手册

## 发布前

本次没有 Rust 编译、数据库联调或 Docker 构建证据。先在隔离环境运行全部测试并修复问题，再考虑生产评估。CI 文件存在不代表 CI 通过。禁止首次联调即使用真实资金。

生成、审查并提交 Cargo.lock，固定 Rust 版本、镜像 digest 和 CI action commit，完成依赖安全与许可证检查。业务必须确认计佣基数、固定费用是否退回、舍入顺序、冻结起点、退款窗口、税费和欠款处置。默认口径不是已经确认的商业合同。

## 数据库与部署

迁移与运行账号分离。运行账号不得为超级用户或表所有者；参考 deploy/runtime-role.sql 并进一步收紧权限。服务器不自动执行 DDL。生产数据库通过可信 TLS 连接（如 sslmode=verify-full），不对公网暴露。迁移先在恢复副本演练。

触发器不防 DB 超级用户；运行角色仍需要钱包更新权限以执行投影。因此不可变账本不等于对任意 SQL 攻击的防篡改存储。

生产 Web 必须在受信反向代理后提供 HTTPS，并设置请求速率、连接数、超时和安全告警。当前没有完整 API 网关限流、MFA、SSO、Prometheus 或高可用部署。

## 访问凭据

初始化后生成第二个管理员并安全分持，避免所有管理员过期失联。默认初始令牌 90 天，后续签发可设 1..365 天。运营、财务、集成、成员使用独立凭据，不要多人共用管理员。

bootstrap 仅在没有任何凭据时执行；没有公开找回后门。全部管理员遗失或过期需受控 DBA 恢复流程并保存独立审计，不是直接改账。

令牌只存浏览器内存，刷新需重新输入；不要放入 URL、截图、工单或仓库。bootstrap 输出包含秘密，勿自动采集进公共日志。双人控制只实现凭据级分离，实际自然人分离依赖组织管理。

## 外部资金事实

capture/refund 是可信业务事实入口，不是匿名支付回调。正式渠道适配器须完成验签、交易状态查询、金额币种校验、订单关联、重放控制与独立对账。

本系统不收款、不退款、不出款；人工核验成功只是财务人员登记外部事实，不能证明银行实际转账。收款方引用也未自动核验。

未来自动出款必须使用稳定提现 UUID 作为渠道业务键。超时查询原交易，不得换号重付。未知结果需持续核查，明确成功或失败后再终结。

## 日常运行

关注 503 重试、锁等待、到期未解冻、负可用余额、长时间执行中 / 未知提现、Outbox 积压。项目有总览与 JSON 日志，但监控告警、死信和自动归档需另行建设。

内部对账采用一致性快照，wallet_differences 最多返回 100 个差异样本。出现差异先暂停出款、保留证据，设计可审计的修复，不能覆盖历史分录对平。

即使内部 ok=true，仍需核对支付机构与银行账单；首版没有账单导入。平衡账本也可能来自虚假上游支付事实。

## 欠款

负可用余额表示退款发生时资金已被占用或已出款。后续收入解冻会抵扣欠款。未执行提现可驳回释放占用后重新申请；执行中和未知状态不能直接驳回。

首版没有线下追偿收款专用入账。不可通过虚构订单或 UPDATE wallets 补余额。后续应实现带唯一收款业务号、核验证据和独立审核的专用分录流程。

## 重试与故障恢复

响应丢失不等于失败。上游应持久保存业务号、原请求和幂等键；用原键重试或查询状态。跨凭据重试不会取得旧作用域的响应，只由业务号唯一性防止重复效果。

中文表单遇到网络 / 5xx 不确定性后锁定原参数并复用原键。关闭或刷新会失去临时上下文，界面提示保存键与核查记录。浏览器内存不是可靠业务队列。

提交前崩溃事务回滚；提交后通过幂等和业务号查询恢复。Outbox 消费者须处理已消费、未 ACK 的重复投递。

## 备份、性能与已知界面限制

备份并演练恢复 PostgreSQL 全部业务数据，不能只备份钱包。制定 PITR、保留与凭据分离策略。

首版没有分区、在线归档、容量压测或 SLO。汇总和内部对账会扫描数据；所有入账触及平台 / 清算钱包，存在平台级热点。Rust 不自动消除数据库行锁瓶颈，必须真实压测后再考虑分片账本或批量聚合。

中文表单账户选择器当前读取前 200 个账户；更多账户可用完整分页列表取得 UUID 并调用 API。尚无海量账户远程搜索选择器。
