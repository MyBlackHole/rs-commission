# 业务模型与一致性设计

## 1. Rust 工作区与业务边界

`apps/console` 是 Dioxus Rust 前端，`commission-client` 是共用 HTTP SDK，`commission-types` 是共用金额、请求/响应和确定性计算。后端 `commission-rs` 保持模块化单体：HTTP 解析和鉴权，service 编排事务，domain 执行纯计算，ledger 统一记账。只有后端启用共享类型的 PostgreSQL 映射；浏览器不引入 SQLx 或数据库运行时。

Web/WASM、Windows/macOS/Linux 桌面和 Android/iOS 移动入口共享界面源码，平台实际验证状态见 VERIFICATION.md。桌面/移动使用系统 WebView，不声称使用原生控件；Web 发布物有工具链生成的 JS/WASM 引导代码。前端业务逻辑不再由手写 JavaScript 实现。

一个平台、多商家、多推广员、CNY 单币种。这不是多 SaaS 租户系统或完整商城。管理员、财务等内部角色能读取整个平台；member 只能访问绑定账户。客户端不直接连接数据库，不允许离线资金记账。不引入 Redis 锁、消息代理或微服务。

一个 PostgreSQL 事务覆盖业务记录、幂等响应、分录、余额投影、审计和 Outbox。

## 2. 核心实体

| 实体 | 职责 |
|---|---|
| accounts | 商家、推广员、唯一平台账户与清算对手账户；上级只在创建时指向已有推广员 |
| referral_bindings | 客户业务 ID 到一级推广员；不可修改，已有订单不可补绑 |
| rules | 创建即发布新版本；可停用，不可覆盖费率等原始参数 |
| orders / allocations | 实付、基数、规则和受益人快照、冻结时间、固定顺序分配与退款投影 |
| refunds | 追加式退款事实、唯一业务号、金额及分配差额 |
| payouts | 申请、审核、金额、收款引用与外部执行状态 |
| journals / ledger_entries | 平衡正负分录；禁止覆盖与删除 |
| wallets | 冻结、可用、占用的投影，不是独立事实源 |
| idempotency | 凭据、操作、客户端键、请求摘要、已提交响应 |
| audit_events / outbox | 与业务同提交的审计与待投递事件 |

## 3. 金额与佣金口径

前后端共同使用 `Money(i64)` 整数分，乘法使用 i128。JSON 金额为字符串。Rust 前端用整数算法解析元与展示小数，不经过浮点或 JavaScript Number；可表示欠款和超出 JS 安全整数范围的金额。单次业务上限为 100000000000000 分。余额累计受 BIGINT 范围限制，溢出必须拒绝事务。

费率用基点，10000 = 100%。佣金池为 `min(计佣基数, 可选封顶, floor(基数×费率/10000)+固定费用)`。两级返佣均从佣金池分出，不向商家重复扣费；向下取整，尾差及不存在的推广员份额留在平台。

规则选择：启用且生效，商家专属优先，priority 大者优先，version 大者优先。基数为 `[min,max)`，生效时间为 `[from,until)`；version 为全局发布序号。

入账按服务器事务时间选择规则并开始冻结。试算返回 binding=false，不保证实际入账继续使用相同规则。历史退款只按原始分配和快照计算，不重查当前规则或推广关系。当前是订单级退款，不支持 SKU/数量级退款、独立运费退款或业绩阶梯提成。

## 4. 累计退款分摊

不能逐人独立取整后简单把所有尾差给商家：多个取整边界同时变化时，一分钱退款可能产生商家的负差额。

采用固定顺序：一级、二级、平台、商家；不存在的推广员不生成项。每一步按剩余金额计算累计目标：

```text
剩余退款 = 累计退款
剩余原额 = 原始实付
当前累计目标 = floor(剩余退款 × 当前原始分配 / 剩余原额)
剩余退款 -= 当前累计目标
剩余原额 -= 当前原始分配
最后一项接收剩余退款
本次冲正 = 当前累计目标 - 上次累计目标
```

对于 `0<=share<=total`，`floor(r×share/total)` 及补数随整数 r 单调不减；逐层保留单调性。因此各方不倒退、差额非负、合计准确，全额退款精确退回原分配。同一累计退款不受拆分次数影响。

固定顺序有微小舍入偏差，不等同于各项独立比例。零原额退回零。应保存顺序与算法版本，不得变更历史订单算法；固定费用退款口径仍须业务验收。

## 5. 业务分户账

正 delta 增加对应账户分类的业务余额，清算账户承接反向分录。这不是完整会计总账，清算余额也不是已核验的银行存款。

100 元订单、10% 佣金池、池内返佣 30%+10%：

```text
清算.available   -10000
商家.frozen       +9000
平台.frozen        +600
一级.frozen        +300
二级.frozen        +100
合计                  0
```

解冻为同账户 `frozen -N / available +N`；提现申请为 `available -N / reserved +N`；出款成功为 `reserved -N / 清算.available +N`；失败/驳回释放占用；退款追加相反方向分录，不修改历史。

数据库延迟约束在 COMMIT 检查 journal 至少两行且合计零，entry 触发器更新钱包。Rust 记账器也检查平衡。冻结与占用不可为负，可用可为负以表达追偿。订单和 allocation 的累计退款只是投影，refunds 保存原始事实。

## 6. 并发、退款与追偿

退款和解冻锁同一订单。记账前按 UUID 排序锁相关钱包，降低死锁风险。每次自动解冻只处理一笔订单；提现申请在钱包锁内检查可用额并占用，防止并发超提。

退款不直接取消提现。可用余额变负后，未执行提现不能审核/开始执行；可驳回原占用抵扣欠款。执行中/未知不能直接驳回，须核验最终外部结果。真实成功保留欠款，明确失败释放占用，后续收入解冻抵扣负余额。

没有任意加余额或线下追偿入账接口，不得虚构订单或 UPDATE wallets 补账。

## 7. 提现状态机

```text
requested -> approved -> processing -> succeeded
    |            |             +----> failed
    +-> rejected <-+           +----> unknown -> succeeded / failed
```

unknown 保留占用，不因超时自动失败，不可直接 rejected。终态不可再次确认。成功必须提供唯一外部流水和核验证据；申请、审核、执行有凭据分离检查。

processing 只是登记执行意图，不调用渠道。未来自动适配器必须使用提现 UUID 等稳定渠道业务键，并实现原交易查询、回调验签和外部对账。数据库事务不能保证跨银行网络恰好一次。

## 8. 幂等、客户端与崩溃恢复

服务端作用域为凭据 ID、操作名、客户端键；路径目标 ID 参与摘要。同键同请求返回首次已提交响应，不同请求返回 409，每次重新认证。缓存响应可能不是最新状态，最新状态用 GET 查询。

占位、业务效果、响应同事务提交。提交前崩溃回滚，提交后响应丢失用原键恢复。订单/退款/提现业务号另有唯一约束；换键或换凭据不能重复记账，但未必返回原响应。

SDK 的 PreparedWrite 冻结路径、规范化请求体和幂等键并绑定会话。前端校验后由用户确认；网络失败、5xx、成功响应无法解析均视为结果未知，只能显式重试原请求。原生端禁止自动重定向和透明重试。前端角色提示不能代替后端授权。

待确认请求和令牌只存内存，尚不支持跨重启恢复。用户退出、刷新前必须记录业务号与键；上游生产集成必须持久保存原请求。共享算法不使客户端结果成为入账凭据。

Outbox 与业务同提交，消费者租约 claim、成功后 ACK；旧租约不能确认新领取，已处理未 ACK 可重投，须按 event.id 幂等。ACK 不递归生成事件。当前没有自动 Webhook、死信、记录清理或归档。

## 9. 信任与安全边界

服务器随机令牌使用 CSPRNG，只保存 SHA-256 摘要；该策略适用于随机高熵令牌，不可直接用于人类密码。前端创建新令牌时应使用 generate-token，而非低熵手工字符串。令牌不写 Cookie、localStorage 或 sessionStorage。

凭据分离不等于自然人分离，管理员可创建多把凭据。MFA、SSO、HTTPS 证书管理、网关限流和自动风控尚未实现。integrator 是可信支付事实生产者，不是匿名回调；虚假 capture 会制造无外部资金支持的账。

触发器无法对抗 DB 所有者/超级用户，任意 SQL 注入或 DB 凭据泄漏也可能破坏投影。不可变账本不是防勒索 WORM；仍需要最小权限、独立备份、监控与外部对账。
