# 业务模型与一致性设计

## 1. 架构与业务边界

模块化单体：HTTP 负责解析和鉴权，service 编排事务，domain 执行不依赖 IO 的金额计算，ledger 统一记账。一个 PostgreSQL 事务覆盖业务记录、幂等响应、分录、余额投影、审计和 Outbox。

一个平台、多商家、多推广员、CNY 单币种。这不是多 SaaS 租户系统或完整商城。管理员、财务等内部角色能读取整个平台；member 只能访问绑定账户。不引入 Redis 锁、消息代理或微服务，避免在尚未验证账务语义时扩大一致性边界。

## 2. 核心实体

| 实体 | 关键职责 |
|---|---|
| accounts | 商家、推广员、唯一平台账户和清算对手账户；上级仅在创建时指向已有推广员 |
| referral_bindings | 客户业务 ID → 一级推广员，不可修改；已有入账订单不可补绑 |
| rules | 一次创建即一个业务版本；可以停用，但费率等原始字段不可修改 |
| orders | 实付、计佣基数、规则和受益人快照、冻结截止时间 |
| allocations | 固定顺序的原始分配与累计退回投影 |
| refunds | 追加式退款事实、唯一外部业务号、金额及分配差额 |
| payouts | 申请者、审核者、金额、收款方引用、外部执行状态 |
| journals / ledger_entries | 每个事件一组平衡正负分录，禁止覆盖与删除 |
| wallets | 冻结、可用、占用的派生投影，不是独立记账事实源 |
| idempotency | 凭据、操作名、幂等键、请求摘要、已提交响应 |
| audit_events / outbox | 与业务同提交的审计和待投递事件 |

## 3. 金额与佣金口径

金额采用 i64 整数分，比例乘法使用 i128。JSON 金额为字符串，前端用 BigInt。单次业务上限为 100000000000000 分。余额累计受 BIGINT 范围限制，溢出应拒绝事务，不能绕回后继续记账。

费率用基点，10000 = 100%。佣金池为 `min(计佣基数, 可选封顶, floor(基数×费率/10000)+固定费用)`。一级、二级返佣均从佣金池分出，不向商家额外叠加；各自向下取整，尾差及无对应推广员的份额留在平台。

规则选择：启用且生效 → 商家专属优先于全局 → priority 大者优先 → version 大者优先。基数区间为 `[min,max)`，生效区间为 `[from,until)`。version 是全局发布序号，不按规则名称分组。

入账用本系统事务时间匹配规则，冻结从该时间开始，不按上游 paid_at 或收货时间回溯。试算返回 `binding=false`，不承诺实际入账继续使用同一规则。订单快照与原始分配确定后，退款不再匹配新规则。

首版是订单级比例退款，不支持 SKU、数量、运费独立退款或销售业绩阶梯提成；当前比例尾差和固定费用退款口径需纳入业务验收。

## 4. 累计退款分摊

不能对每个受益人独立 `floor(原分配×累计退款/实付)` 后把所有差额给商家。几个受益人的取整边界可能同时跨过，导致本次只退 1 分、其他人合计多退 2 分，商家差额反而为负。

采用固定顺序的累计逐层比例分摊：一级、二级、平台、商家；不存在的推广员不生成项。

```text
剩余退款 = 累计退款
剩余原额 = 原始实付

依次处理每个分配（最后一项直接接收剩余）：
    当前累计目标 = floor(剩余退款 × 当前原始分配 / 剩余原额)
    剩余退款 -= 当前累计目标
    剩余原额 -= 当前原始分配

本次冲正 = 当前累计目标 - 上次累计目标
```

当 `0<=share<=total` 时，`floor(r×share/total)` 和补数 `r-floor(...)` 都随整数 r 单调不减。逐层应用保留单调性。因此每方累计退回不倒退、每次差额非负、退款差额合计准确，全额退款精确退回原始分配。同一累计退款不受拆分次数影响。

该算法具有固定顺序造成的微小舍入偏差，不声称等同于逐项独立比例。原始金额为零的项退回零。永久保存顺序和算法版本，不能在历史订单上更换舍入算法。

## 5. 业务分户账

正 delta 增加对应账户分类的业务余额。通常受益方余额为正，清算对手账户承接反向分录。这不是完整会计总账；清算余额也不等于已核验银行存款。

100 元、10% 佣金池、池内返佣 30%+10%：

```text
清算.available      -10000
商家.frozen          +9000
平台.frozen           +600
一级推广员.frozen     +300
二级推广员.frozen     +100
合计                     0
```

解冻：同账户 `frozen -N / available +N`。提现申请：`available -N / reserved +N`。出款成功：`reserved -N / 清算.available +N`。失败或驳回：`reserved -N / available +N`。退款新增相反方向业务分录，不修改旧分录。

数据库延迟约束触发器在 COMMIT 时检查每个 journal 至少两行且合计零；entry 插入触发器同步更新钱包。Rust 记账器也先检查平衡。冻结和占用不可为负，可用余额可为负，明确表达已出款后追偿。

订单、allocation 的累计退款是投影，退款原始事实单独追加至 refunds。原始金额和快照不可覆盖。

## 6. 并发与退款追偿

退款和解冻先锁相同订单行。分录写入前按 UUID 排序锁定所有相关钱包，减少逆序死锁。每次解冻事务只处理一笔订单，不跨订单积累锁。提现申请在钱包行锁内检查可用额并占用，避免两个请求消费同一余额。

退款不直接取消提现。退款后若可用为负，未执行提现不能审核或开始执行；可驳回原占用抵扣欠款。执行中或未知结果不允许直接驳回，必须核验外部最终状态。真实成功则保留欠款；明确失败则释放占用抵扣欠款；后续收入解冻也会抵扣负余额。

没有任意加余额入口，也没有线下追偿收款专用接口。不得通过虚构订单或 UPDATE wallets 伪造欠款回收。

## 7. 提现状态机

```text
requested -> approved -> processing -> succeeded
    |            |             |          [终态]
    +-> rejected <-+           +-> failed [终态]
                               +-> unknown -> succeeded / failed
```

unknown 保留占用，不因网络超时自动失败，也不能直接 rejected。终态不能再次确认出款。成功必须提供唯一外部流水号和核验说明。申请、审核及执行核验有凭据分离检查。

processing 只是登记执行意图，不调用渠道。外部执行应以提现 UUID 为稳定业务引用。未来自动适配器必须使用渠道幂等、原交易查询恢复、回调验签和外部对账处理不确定性。数据库事务不能提供跨银行网络的恰好一次执行。

## 8. 幂等、崩溃和事件

幂等作用域为凭据 ID＋操作名＋客户端键，路径 ID 参与请求摘要。同键同请求返回首次成功响应，同键不同请求返回 409；认证每次重查。缓存响应可能不是记录最新状态，最新状态应 GET。

幂等占位、业务效果和响应同事务提交。提交前崩溃全部回滚；提交后响应丢失用原键恢复。业务订单、退款、提现外部编号还有全局唯一约束，换键换凭据也不能重复记账，但会返回业务冲突而非旧响应。

Outbox 同事务写入，消费者按租约 claim，处理成功后 ACK。过期可重新领取，旧租约不能 ACK 新租约。消费者必须按 event.id 幂等，已处理但尚未 ACK 的事件可能重投。ACK 不生成新 Outbox，避免递归。

没有自动 HTTP Webhook、死信告警、幂等记录清理或事件归档。生产须单独制定保留和归档策略。

## 9. 信任与安全边界

访问令牌为 CSPRNG 生成的 256 位随机值，只存 SHA-256 摘要。它不是人类密码，不能把此策略照搬为人类密码存储。格式校验无法证明客户端随机性，应使用内置生成器。前端只在内存保存令牌，不使用 Cookie、localStorage 或 sessionStorage。

凭据分离不等于自然人分离，管理员可以签发多把令牌；应分别交由不同人员持有。MFA、SSO、HTTPS、代理限流和自动风控未实现。

integrator 是可信支付事实生产者，不是匿名渠道回调。未验证真实支付就调用 capture，会产生没有外部资金支持的账。上游必须核实支付状态、金额和业务关联。

触发器不能对抗 DB 所有者或超级用户。运行角色仍需部分钱包更新权限以执行投影；任意 SQL 注入或 DB 凭据泄露可能破坏数据。不可变账本不是防勒索 WORM，需要独立备份、最小权限、告警与外部对账。
